# 智能拍照学习助手（高数拍搜）

> **从「给答案」到「懂你哪里不会」。**
>
> 拍一道高数题，它不满足于告诉你答案，而是判断你卡在哪个知识点、为什么卡住，
> 然后生成针对性的练习与诊断，把每一次提问都变成画像的一块砖。

技术栈：Vue 3 + Vite · FastAPI + SQLModel · DeepSeek 多模态大模型

---

## 一、这个项目解决什么问题

作业帮、小猿搜题能回答「这道题怎么做」，但回答不了「**你到底哪里不会**」。

二者差别不在识别精度，而在**数据是否闭环**：搜题工具把每次提问当成一次独立查询，用完即弃；学生刷了一百道题，系统对他依然一无所知。

我们做的是后半句。核心判断只有一条：

> 一次答疑如果只产出答案，那是浪费。它应该同时产出「这个学生在这个知识点上的状态」。

于是有了下面这条闭环——它是整个项目的骨架：

```
拍照答疑 → 学生反馈 → 画像更新 → 诊断报告 → 针对性组卷 → 错题本 → 标记掌握
    ↑                                                                    │
    └──────────────────── 回流：数据再次沉淀 ─────────────────────────────┘
```

七步里每一步都在给画像添砖：答疑贡献知识点标签，反馈贡献错因，自测贡献对错，错题本贡献重复错次数。学生用得越久，诊断越准。

### 三个智能体各管一段

| 角色 | 职责 | 边界 |
|---|---|---|
| **识别 Agent** | 把照片变成结构化输入：OCR 定位题号坐标、精确切图、版面校验 | 不做内容理解 |
| **诊断 Agent** | 知识点打标、错因归类、画像更新，回答「这个同学哪里不会」 | 不做讲解 |
| **辅导 Agent** | 分步解析、交互式引导、按需换讲法 | 不做长期记忆 |

## 二、设计理念：规则引擎定骨架，LLM 填内容

这是贯穿全项目的第一原则。

**为什么不让大模型接管一切？** 因为三件事它做不好，而这三件事恰恰是产品的可靠性底线：

| 环节 | 用规则 | 用 LLM | 结果 |
|---|---|---|---|
| 薄弱度算分 | ✅ 确定性公式 | ❌ 每次结果不同 | 可复现、可解释、可审计 |
| 组卷抽题 | ✅ 按薄弱点 + 难度阶梯 | ❌ 可能出重复题 | 稳定、可控 |
| 客观题判分 | ✅ 答案归一化匹配 | ❌ 会算错 | 零成本、100% 一致 |
| 分步讲解 | — | ✅ | LLM 的真正价值所在 |
| 诊断报告 | ✅ 规则版兜底 | ✅ 深度版 | **不花钱也能用** |
| 手写解答阅卷 | — | ✅ | 只有它能做 |

因此每个 AI 功能都有**降级路径**：诊断报告有零 token 的规则版、解析有库内原文、阅卷失败可回退自评。**API 挂了或没余额，产品不会瘫。**

## 三、技术亮点

### 1. 搭车打标：一次调用干两件事

答疑那一次模型调用，除了返回分步讲解，**同时**返回学科、章节、知识点、难度、错因候选、反馈选项。

这是整个画像系统成立的**成本前提**——如果打标要额外调一次模型，每道题的成本会翻倍，个性化服务在经济上就不成立。实测这一设计让「画像系统的边际成本」接近于零。

### 2. 让学生自己当诊断医生

原本的设计是让模型自动判断错因。论证后推翻：

> 模型只拿到「题目 + 答案」这个结果，看不到草稿纸，也看不到学生算了三遍还是第一遍就算错。它**分不清「真不会」和「粗心」**——而这两件事的处理方式完全相反：前者要补知识，后者只要提醒审题。

于是改成：模型预生成 4~6 个针对本题的候选（强制包含「粗心」「看错题」这类通用项），学生自己多选，还能补充自己的话。

学生比任何模型都清楚自己为什么错。

### 3. 错因权重：乘性主因子，不是微调项

薄弱度公式：

```
薄弱度 = 错误率 × (0.15 + 0.85 × 错因权重) × 时间衰减
```

关键在于错因权重**乘以**错误率，而不是加减一个修正值。若是加法，粗心累计几次照样能突破阈值；写成乘法，粗心永远被压在一个低配系数上。

实测区分度（同样错一次，只有错因不同）：

| 错因 | 权重 | 薄弱度 | 判定 |
|---|---|---|---|
| 完全没思路 | 1.2 | 1.00 | 薄弱 |
| 概念没理解 | 1.0 | 1.00 | 薄弱 |
| 漏看条件 | 0.4 | 0.49 | 薄弱 |
| 计算失误 | 0.3 | 0.41 | 薄弱 |
| **粗心算错** | **0.2** | **0.32** | **不判薄弱** |
| **看错题** | **0.2** | **0.32** | **不判薄弱** |

配合「低级错误不计入求助次数」，单次粗心的薄弱度是 **0.00**——完全不进薄弱池。学生不会因为马虎被系统认为基础差。

这条公式还带来四个工程性质：

| 性质 | 机制 | 效果 |
|---|---|---|
| 粗心不污染 | 低权重 + 不计求助 | 单次粗心 0.00 |
| 信号可叠加 | 分子含求助与自测错 | 反复出问题会累积 |
| **可自我修复** | 做对后分母增大、错误率下降 | 反馈过「不会」但后来做对两次，0.50 → **0.25 回落** |
| 时间衰减 | `exp(-天数/30)` | 陈旧结论自动淡化，不做黑历史 |

### 4. OCR 只做「眼睛」，不做「大脑」

OCR 在数学场景下的能力边界非常清晰：**定位极准，识别极差**。

实测：RapidOCR 能稳定检出题号 `【140】`（置信度 0.79~0.87），但会把 `f(α)(1-sinα)` 认成 `f()(|3—1)g()`。

所以分工是：**OCR 只负责定位题号坐标来精确切图，内容理解全部交给多模态模型**。这个边界划清后，切图的"顶部混入上一题末行"问题被根治——10 道样本里 7 道走 OCR 精确定位、零残留，3 道自动回退模型坐标。

### 5. 扫描版 PDF 的自动化知识库

原始数据源是一本 501 页的**扫描版**吉米多维奇精选精解——**零文本层，直接抽文字一个字都抽不出来**。

处理路径：

```
书签目录（100 条）→ 章节骨架 → LLM 细分知识点（900 个，含说明/公式/难度）
                                      ↓
        页面渲染成图 → 多模态模型结构化提取 → OCR 精密切图 → 题库入库
```

整条管线脚本化，带缓存、断点续跑、幂等 upsert——500 页可以无人值守跑完，中途断了下一次只补缺失的页。

### 6. 题干与解析分离：练习时不该看到答案

最初的裁剪是「一题一图」，把题干、选项、**解析**全裁在一张图上。结果是练习时题目自带答案——判题沦落为"请对照草稿自己判断对错"。

现在的做法是**一题三图**：

| 图 | 内容 | 何时展示 |
|---|---|---|
| `_stem.png` | 题干 + 选项 + 题内坐标系/函数图像 | 答题时 |
| `_sol.png` | 书上解析 | **判分后** |
| 整题图 | 全部（兼容与校对用） | 人工校对页 |

分界点的确定是两段式：**模型给语义分界**（它读得懂"哪行是解析"），**OCR 行边界做几何校正**（它给得出"行在哪"）。校正有三重锚点——选项行下限、解析起始词（解/证明/由/因为/根据）、行顶部吸附，避免切在行中间或把解析首行塞进题干。

全量 1348 题实测：**83% 成功分离**；其余 17% 因题干过短（如一行填空题）或缺少可靠分界点，按设计回退整题图——**宁可给整题图，也不给切错的图**。

### 7. 断网续传与幂等

移动端的现实是网络会断、App 会被杀。设计上：

- 端侧生成 `client_question_id`（UUID），服务端唯一约束，**重复提交返回已有结果**
- `failed` 状态的记录可凭同一 ID 重试
- 规则：幂等键由客户端掌控，服务端不做"猜"

### 8. 上下文分层与成本实测

画像注入看着很美，但成本得算清楚。我们做了 A/B 实测，结论**推翻了事先的推演**：

| 指标 | 注入前 | 注入后 | 变化 |
|---|---|---|---|
| prompt tokens | 285 | 363 | +27.3% |
| **completion tokens** | 817 | 1029 | **+26%** |
| 总成本 | — | — | **约 +5%** |

反直觉的点：**completion 也涨了**——带着画像上下文，模型会更啰嗦。

因此画像不是无条件注入。分层策略是：L1 长期画像（Top5 薄弱 + Top3 优势，硬上限 1000 字符）、L2 会话摘要（最近 4 轮）、L3 短期窗口，按场景选择注入哪几层；诊断与报告场景才带 L1。

## 四、过程中推翻的设计

比"做了什么"更能说明问题的，是"改掉了什么"。以下每一条都是论证或实测后推翻的：

| 原方案 | 为什么不成立 | 改成 |
|---|---|---|
| 模型自动诊断错因 | 只有错题结果、没有过程信息，分不清真不会与粗心 | **学生自报**（候选搭车预生成 + 自定义） |
| 错因权重做成加法微调 | 粗心累计几次仍能突破阈值 | **乘性主因子**（0.15 + 0.85×权重） |
| 多选错因取平均 | 实测「粗心+概念不清」平均后 0.33，低于阈值 → **真问题被漏判** | **取最强错因**（改后 0.50 判薄弱） |
| 用 OCR 提取题干文本 | 公式识别极差，`f(α)(1-sinα)` → 乱码 | **OCR 只定位坐标**，内容交给多模态模型 |
| 题目一题一图 | 图上带着解析，练习时等于给答案 | **题干/解析分离**（三图） |
| 图片不上云（队友 demo 的卖点） | 与"多模态直接识图"的产品路线冲突 | **图片直传大模型**，隐私靠最小化字段与清除入口保障 |
| 画像注入必然省钱 | A/B 实测 prompt +27%、completion +26%，净增约 5% | **按场景选择性注入**，不无条件带 |
| 前端引组件库 + 图表库 | 样式覆盖冲突、体积膨胀，而需求只有四屏 | **手写 CSS 变量 + SVG 雷达图**（产物 gzip 约 130KB） |

## 五、系统架构

```
┌─────────────────────────────────────────────────────────────┐
│  端侧采集层    拍照 / 文字 / 搜书 → 本地缓存 + 幂等 ID        │
├─────────────────────────────────────────────────────────────┤
│  云端计算层    FastAPI + SQLModel                           │
│               题库 / 画像 / 诊断 / 组卷 / 检索管线            │
├─────────────────────────────────────────────────────────────┤
│  AI 智能体层   识别 Agent → 诊断 Agent → 辅导 Agent          │
│               搭车打标：讲解 + 标签 + 错因候选，一次调用       │
├─────────────────────────────────────────────────────────────┤
│  数据与知识层  SQLite（开发）/ MySQL（部署）                  │
│               900 知识点 · 题库 · 题目三图 · 用户画像         │
└─────────────────────────────────────────────────────────────┘
```

| 层 | 选型 | 说明 |
|---|---|---|
| 后端 | Python 3.13 · FastAPI · SQLModel · Pydantic Settings · httpx | 全参数绑定，无手写 SQL |
| 数据库 | SQLite（开发）/ MySQL（部署） | `DATABASE_URL` 一行切换 |
| 存储 | 本地磁盘 + `StorageBackend` 抽象 | 换 OSS 时业务代码零改动 |
| AI | DeepSeek 多模态（OpenAI 兼容协议） | 答疑 + 打标同次调用 |
| 前端 | Vue 3 + Vite + vue-router（hash） | 不用 Pinia / UI 库 / 图表库 |
| 公式渲染 | KaTeX | 解析里 LaTeX 必须真渲染，不能显示源码 |

**前端刻意的"轻"**：四屏应用不需要状态管理框架（`localStorage` + `ref` 够用）、不需要组件库（手写 CSS 变量体系更可控）、不需要图表库（雷达图手绘 SVG 约 130 行，还能做章节下钻）。省下的体积与冲突成本，比省下的开发时间更值。

## 七、快速开始

### 前置条件

| 依赖 | 版本 | 说明 |
|---|---|---|
| Python | 3.11+ | 安装时勾选 **Add Python to PATH** |
| Node.js | 18+ | 前端构建 |
| DeepSeek API Key | — | [platform.deepseek.com](https://platform.deepseek.com)；**不填也能用除 AI 外的全部功能** |

### 三步启动（Windows）

```
① 双击 setup.bat      → 建虚拟环境、装依赖、生成 .env
② 编辑 backend\.env   → 填入 DEEPSEEK_API_KEY=你的密钥
③ 双击 start.bat      → 起前后端并自动打开浏览器
```

- 前端 http://127.0.0.1:5173
- 接口文档 http://127.0.0.1:8000/docs
- 题库校对页 http://127.0.0.1:8000/review

### 手动启动（macOS / Linux）

```bash
cd backend
python -m venv .venv
.venv/bin/pip install -r requirements.txt     # Windows: .venv\Scripts\pip
cp .env.example .env                          # 填 API Key
.venv/bin/python -m uvicorn app.main:app --reload --port 8000

cd ../frontend && npm install && npm run dev  # 另开终端
```

依赖慢可换镜像：`-i https://pypi.tuna.tsinghua.edu.cn/simple` / `--registry=https://registry.npmmirror.com`

### 自带数据

仓库内 `backend/dev.db` 与 `backend/kb_images/` 已包含构建好的知识库，克隆即可用：**1348 道题 + 900 个知识点 + 每题题干图/解析图**。

整题图（仅人工校对页使用，占图片总量约 1/3）未随仓库分发以控制体积，需要时运行 `scripts/kb/08_recrop_all.py` 自动重建。

**查看演示账号**：进入「我的」页 → 点击「演示数据（1001）」→ 切到「诊断」页看雷达图与诊断报告（含一周学习轨迹、错题本、画像）。

### 常用配置（backend/.env）

| 配置 | 默认 | 说明 |
|---|---|---|
| `DEEPSEEK_API_KEY` | 空 | 必填；不填时 AI 接口返回 503，其余功能正常 |
| `DEEPSEEK_MAX_TOKENS` | `32000` | **推理模型思考 token 计入**，过小会导致正文为空 |
| `DEEPSEEK_MODEL` | `Deepseek-V4.1-Flash` | 模型名 |
| `DATABASE_URL` | `sqlite:///./dev.db` | 切 MySQL：`mysql+pymysql://user:pwd@host:3306/photo_tutor?charset=utf8mb4` |
| `UPLOAD_DIR` | `./uploads` | 用户上传图片目录 |

### 常见问题

**没有 API Key 能用吗？** 除 AI 功能（答疑、诊断报告 LLM 版、阅卷、解析求助）外全部可用：题库浏览、组卷、客观题判分、画像统计、雷达图、错题本。

**端口被占用？** 后端 `--port 8001`，前端启动前 `set VITE_BACKEND=http://127.0.0.1:8001`。

**全量提取报「空正文」？** 推理模型的思考与正文共享 `max_tokens`，调大 `DEEPSEEK_MAX_TOKENS`（提取脚本已设 32000）。
